# Mastery — one profession per character, ranked by playtime

A character takes up **one** of eight professions and keeps it. Rank is earned by
time actually played on that character, not by XP and not by repeating an
action. Each rank unlocks recipes, which live in the Alduinak plugin and are
gated on a marker spell the server grants.

- Client piece: `skymp5-client/src/services/services/masteryService.ts` (default **K**)
- Front piece: `skymp5-front/src/features/masteryMenu/`
- Server piece: `skymp5-server/ts/systems/masterySystem.ts`

---

## The ladder

| Rank | Reached at | Marker spell index |
|---|---|---|
| Novice | on choosing | 0 |
| Adept | 10 hours | 1 |
| Expert | 40 hours | 2 |
| Master | 100 hours | 3 |

Thresholds come from `masteryRankHours` in `server-settings.json` (default
`[10, 40, 100]`). Novice is always 0 and is not listed.

Playtime accrues a minute at a time while the character is in the world and not
idle. Idle is `AfkSystem`'s own clock, so the same input that keeps a player from
being AFK-kicked keeps their mastery ticking. The idle cutoff is
`masteryIdleMinutes` (default 5), deliberately far shorter than the 20-minute
AFK kick — standing still in a tavern for six minutes stops the clock, it does
not disconnect anybody.

Playtime is **per character**: the record lives on the actor form, so an alt
starts at Novice.

## Authoring the plugin

### Why marker spells and not perks

Recipe gating has to satisfy two independent filters, and only one mechanism
passes both:

- **The crafting menu** is pure vanilla Skyrim. SkyMP has no crafting-menu code,
  so a recipe is hidden only if the *local* game state fails its condition —
  which means SkyMP must sync whatever the condition reads.
- **The server** re-validates every craft in `CraftService`, but it only knows 17
  condition functions. An unregistered function evaluates to **true**.

`HasSpell` (CTDA function index 264) is the only per-player gate that passes
both. Spells are stored in the actor's changeform (`learnedSpells`), synced to
the client at spawn and live mid-session, and cannot be dropped or traded.

Do **not** use perks: `HasPerk` is unregistered server-side (so it evaluates
true and the server would accept a forged craft) and SkyMP never syncs perks to
the client (so the menu would hide the recipe from everyone forever). Token
items work but are tradeable, so two players can share one mastery.

### 1. Create 32 marker spells

Eight professions × four ranks. Each must be:

- a **SPEL** record, archetype **Ability** or **Lesser Power**, with **no magic
  effects** — it must be inert in game.
- **standalone**: not attached to any RACE or NPC_ record. Spells inherited from
  a base record are merged into the actor's spell list and *cannot be removed*
  (`PapyrusActor.cpp` refuses), which would make an admin reset impossible.

Naming suggestion: `AldMastery_Blacksmith_Novice`, `..._Adept`, and so on.

### 2. Register the form ids

Put them in `server-settings.json` under the `skymp5-client`-sibling top level,
in rank order — Novice, Adept, Expert, Master:

```json
"masterySpells": {
  "blacksmith": [66125825, 66125826, 66125827, 66125828],
  "alchemist":  [66125829, 66125830, 66125831, 66125832]
}
```

Decimal or hex-as-number both work. Professions absent from the map still rank
up; they simply grant nothing, so you can ship one profession at a time.

`server-settings.json` is gitignored and lives only on the server box — it has
to be edited there by hand.

### 3. Author the recipes

Each new recipe is a **COBJ** record with:

- the workbench keyword the recipe belongs to (`CraftingSmithingForge`, and so on),
- its ingredients and output,
- **one condition**: `HasSpell`, parameter = the marker spell for the rank that
  should unlock it, **Run On = Subject**.

`Run On` must be Subject. `ConditionsEvaluator` only accepts `Subject`, `Target`
and `Reference`; anything else fails the condition outright.

A Master keeps every marker below their rank, so condition each recipe on the
rank it belongs to rather than trying to express a range.

Two engine constraints worth knowing:

- **Tempering recipes can never be gated this way.** `CraftService` hard-blocks
  recipes whose bench keyword is `ArmorTable` or `SharpeningWheel`.
- The server matches ingredients **exactly**. A recipe whose inputs do not match
  the packet exactly is rejected, so recipes with optional ingredients will not
  work.

### 4. Ship it

Adding records to the plugin means regenerating the client manifest and
restarting the server — espm is read once at startup and the recipe list is
cached for the process lifetime.

## Admin reset

`MasterySystem.resetCharacter(ctx, actorId)` clears the choice and revokes the
markers so the character can pick again. It is not yet wired to a command.

## Wire protocol

```
Client -> Server: { "customPacketType": "masteryInfoRequest" }
Server -> Client: { "customPacketType": "masteryMenu", "profession", "rank",
                    "hours", "rankHours", "professions" }
Client -> Server: { "customPacketType": "masteryChoose", "profession": "<id>" }
Server -> Client: { "customPacketType": "masteryNotice", "text" }
```

## Settings reference

| Key | Default | Meaning |
|---|---|---|
| `masteryRankHours` | `[10, 40, 100]` | Hours for Adept, Expert, Master |
| `masteryIdleMinutes` | `5` | Idle minutes that stop accrual |
| `masterySpells` | `{}` | Profession id to `[novice, adept, expert, master]` form ids |
| `masteryMenuKeyCode` | `K` | DirectInput scan code, in the `skymp5-client` block |
