# Weather: one sky per region, shared by everyone in it

Vanilla Skyrim rolls the weather on each client alone, so two players standing
together could see rain and sunshine. The server now owns the sky: every
weather region of the plugins gets its own weather, rolled from that region's
own list and kept for 30 to 90 real minutes, and every client standing in the
region shows it. Interiors keep the weather of the last place outside, a relog
inside an inn included. Staff can hold a weather on a region from the Personal
Menu's Admin > Weather sub-tab.

- Server piece: `skymp5-server/ts/systems/weatherSystem.ts` (regions, rolls, who is where, packets, admin API)
- Region data: `skymp5-server/ts/systems/weatherRegions.ts`, generated by `misc/gen-weather-regions.py` from the load order (rerun it after a plugin change, never edit it)
- Client piece: `skymp5-client/src/services/services/weatherService.ts` (applies the packet, re-applies after doors and fast travel)
- Admin panel: `adminSystem.ts` (packets), `adminMenuService.ts` (passthrough), `skymp5-front/src/features/adminPanel/weatherTab.tsx` (the Weather sub-tab)
- Sidecar: `build/dist/server/weather-state.json`, the current weather of every region, so a restart continues them
- Optional live file: `build/dist/server/weather-regions.json`, a hand-edited region list that replaces the generated one when present
- Character record: `private.weatherRegion`, the last exterior region the character stood in

The time sync (`timeSystem.ts`) and this system share nothing: durations run on
the box clock, and the client never touches the calendar globals for weather.

---

## Regions

The generator walks every plugin of `loadOrder` and keeps the last override of
each REGN, WTHR and WRLD record, so a mod that reshapes a region or retunes a
weather wins like it does in game. A region counts when it names a worldspace
and carries a weather list (Dawnguard overrides every vanilla Tamriel region,
Dragonborn adds Solstheim's seven). Regions are kept in the game's lookup
order, weather priority first, so the overlapping vanilla polygons resolve the
way the engine resolves them: the six `NoPrecip` pockets (95) over Falkreath
(95), Mountains (90), Winterhold and the Labyrinthian (65), Riften and Snow
(60), Reach and Fall Forest (55), Volcanic Tundra (53), Pine Forest and Tundra
Marsh (52), then Coast and Tundra (50).

Two rules differ from a plain dump:

- A child worldspace on its parent's terrain (WRLD `PNAM` "Use Land Data") or
  holding a City map marker drops its own regions and is folded into the parent
  region around it: Whiterun and the Dragonsreach porch, Solitude into Tundra,
  Windhelm into Snow, Riften into the Riften fog region, Markarth into the
  Reach. Walking through a city gate never changes the sky.
- Worlds whose sky is scripted stay out (`WORLD_DENYLIST`): Sovngarde, the
  Soul Cairn, Apocrypha, Skuldafn and the FX light world. A player there gets
  no region and the vanilla sky runs; back in Tamriel the home region's weather
  returns.

The live load order gives 45 regions over 16 worlds (Tamriel, Solstheim, the
Forgotten Vale, Blackreach and the small quest worlds such as Japhet's Folly
and the Blue Palace wing) and a catalog of 108 weathers. The generator prints
what it folded and skipped, and `--dump` lists every region with its priority,
polygons and weather chances.

Every city, town and fort marker of the Teleport tab resolves to a region
(checked against the marker positions of Whiterun, Riften, Solitude,
Windhelm, Markarth, Raven Rock, Falkreath, Winterhold, Riverwood, Morthal and
Dawnstar); a spot outside every polygon, such as far out at sea, keeps the
last region the player stood in.

## How a weather is picked

Each region rolls one entry of its own list, weighted by the plugin's chances
and never repeating the current one, and keeps it for `weatherMinMinutes` to
`weatherMaxMinutes` real minutes (30 to 90). Every region keeps its own clock
whether or not anyone is there, so the admin tab's countdowns are honest.
A roll logs `[weather] tundra: SkyrimStormRainTU for 47 min`.

Chances are the vanilla ones, so the Tundra is clear or cloudy nine times in
ten and rains once; Falkreath is fog and rain; Winterhold is always a storm.

## Who gets which weather

Every 2 s the server looks at each online player: in a listed worldspace the
first region whose polygon holds their position is theirs (an area without a
polygon covers the whole world); inside a cell they keep the last exterior
region (`private.weatherRegion` on the character, so a relog in an inn keeps
it); in an unlisted world they get none. A packet goes out only when the
region, its weather or its start changed for that player, so riding along a
border never flips the sky back and forth.

```
Server -> Client  { customPacketType: "weather", region, name, weatherId, weather, endsAt, transition, gameSettings? }
Client -> Server  { customPacketType: "weatherRequest" }
```

`region` null tells the client to release its override. `weatherId` is the
WTHR form id, `weather` its editor id, `endsAt` the epoch ms the weather runs
out (0 while forced until cleared), `transition` the fade mode below.

The client stores the packet and applies it on the next update (natives are
unavailable in the packet handler). Right after a load screen the weather is
set outright with `forceActive`, so the template save's own sky never fades
over; later changes fade with `setActive`. Every 10 s, and after each cell
load, the client checks that the sky outside still shows the applied weather
once no fade is running, and forces it again when a door, fast travel or the
engine dropped it. `loadGame` (login and character switch) resets that state
and sends `weatherRequest`, which makes the server answer within one poll.

## Transitions

The engine advances a weather fade in game hours, and the realm's clock runs
game time at 1:1, so a normal fade is far slower than in vanilla. The packet
carries the mode (`weatherTransition`): `accelerate` (default) uses the
engine's accelerated fade, `instant` switches the sky outright, `normal` is
the vanilla fade. `weatherGameSettings` passes `fWeatherTransMin`,
`fWeatherTransMax` and `fWeatherTransAccel` floats that every client applies
once, so the fade speed can be tuned from `server-settings.json` without a
client rebuild. The first test measures it: if a fade still runs five minutes
after `setActive`, the client logs `WeatherService: fade still at 0.xx five
minutes after setActive` to `skyrim-platform.log`.

## The state sidecar

`weather-state.json` next to the server holds one entry per region id:

```json
{
 "tundra": { "weatherDesc": "10a240:Skyrim.esm", "weatherId": 1090112, "startedAt": 1790000000000, "endsAt": 1790002700000, "forced": false }
}
```

It is rewritten atomically (temp file plus rename) on every roll and every
admin change, a few times an hour. On boot an entry still running, or forced
until cleared, continues; the rest roll fresh (a timed force whose time
passed while the server was down included), and the boot line says how many
of each:
`WeatherSystem: 45 regions over 16 worlds, 108 catalog weathers, 30-90 min,
transition accelerate; ./weather-state.json: 12 kept, 33 rolled`. A missing or
unreadable file rolls everything. `wipe-world.js` resets it to `{}`, and
Build server keeps it.

`weather-regions.json` is optional: when it sits next to the server it
replaces the generated list. Write it with `python misc/gen-weather-regions.py
--json build/dist/server/weather-regions.json`, then delete or merge entries
(same shape as `WEATHER_REGIONS`: `id`, `name`, `areas: [{ world, poly? }]`,
`weathers: [{ desc, edid, chance }]`). Entries that fail validation are
dropped with a log line, and a weather that is not a WTHR of the load order
is dropped from any list. Build server keeps the file and `wipe-world.js`
backs it up and leaves it alone, like `NPC-Spawns.json`.

## Settings

All optional, in `server-settings.json`:

| Key | Default | Meaning |
|---|---|---|
| `weatherEnabled` | `true` | `false` sends no packets; clients keep the vanilla sky |
| `weatherMinMinutes` | `30` | Shortest weather, real minutes (1 to 1440) |
| `weatherMaxMinutes` | `90` | Longest weather (at least the minimum, at most 1440) |
| `weatherTransition` | `"accelerate"` | `accelerate`, `normal` or `instant` |
| `weatherGameSettings` | none | `{ "fWeatherTransMin": .., "fWeatherTransMax": .., "fWeatherTransAccel": .. }`, applied once per client |

## Admin > Weather

Every tier gets the sub-tab (`weather` cap, switchable per tier through
`adminTierCaps`; a server without the cap never shows it). It lists every
region, the admin's own first and marked "(here)", with the current weather
in plain words (`SkyrimOvercastRainTU` reads "Overcast Rain (tundra)"), the
time left or "until cleared", a lit dot while forced and how many players
stand in it; the countdown ticks from the server's clock. Pick fills the
form's Region from a row and Clear on a row releases it.

The form: Region ("The region I am in" or any region), Weather (the picked
region's own weathers with their chances first, then the whole catalog, the
FX and editor weathers last), Minutes (blank holds until cleared, else 1 to
1440). Force puts the weather on the region for everyone in it within one
poll and Clear rolls one of the region's own weathers again with a fresh
30 to 90 minute clock. Both toast the result and write an admin.log line:
`profile 12 (gm) forced weather SkyrimStormSnow on region tundra until
cleared`, `profile 12 (gm) cleared the weather on region tundra`. A forced
weather survives restarts by design, so an event storm nobody cleared shows
as forced until someone presses Clear.

```
Client -> Server  { customPacketType: "adminAction", action: "weatherList", catalog? }
                  { customPacketType: "adminAction", action: "weatherSet", region, weather, minutes }
                  { customPacketType: "adminAction", action: "weatherClear", region }
Server -> Client  { customPacketType: "adminWeather", regions: [...], weathers?: [...], at }
```

`region` "" means the admin's own (refused with "You are not in a weather
region" in Sovngarde); `weather` is a catalog desc or editor id; the catalog
comes only with a `weatherList` that asks for it, the list after every change.

## Regenerating the data

After a plugin change touching REGN or WTHR records:

```
python misc/gen-weather-regions.py
```

reads `build/dist/server/server-settings.json` for the load order and `dataDir`
(`--settings` and `--data` override them), rewrites `weatherRegions.ts` and
prints the fold and skip lines. Commit the result and Build server.
