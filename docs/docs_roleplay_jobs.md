# Passive jobs: carry a load, get paid

`Jobs.json` next to the server lists carry jobs: a pickup spot, a dropoff spot
and the load in between (hay bales, blocks of wood, baskets of fish). A player
standing at a pickup sees an offer where the activate prompt usually is,
`[E] Carry hay (10 gold)`, and presses Activate to take the work. The character
goes into a vanilla carry pose, is forced to walk and cannot fight, and walking
into the dropoff pays the gold, plus any `Rewards` items of the job (hay
hauling pays Straw, fishing a raw fish). Each character can make 10 paid trips
in any 12 hours, counted across every job and while offline. Nothing is placed in the
world and no plugin record is needed; the file is watched, so edits apply
without a restart, and the Jobs sub-tab of the Personal Menu places jobs in game.

- Server piece: `skymp5-server/ts/systems/jobSystem.ts` (file, offers, trips, pay, hooks, admin API)
- Client pieces: `skymp5-client/src/services/services/jobService.ts` (offer and Activate),
  `interactionPromptService.ts` (shows the offer), `playerActionService.ts` (Put down),
  `restraintService.ts` (the carry pose, through the existing `carryState` packet)
- Admin panel: `adminSystem.ts` (packets), `adminMenuService.ts` (passthrough), `skymp5-front/src/features/adminPanel/jobs.tsx` (Jobs sub-tab)
- Live file: `build/dist/server/Jobs.json` (gitignored, edited by hand on the box or from the panel)
- Character record: `private.jobs = { trips: [epoch ms, ...] }`, the paid deliveries of the last window

The server runs normally without `Jobs.json`: it logs
`[jobs] ./Jobs.json not found, no jobs (boot)` and offers nothing.

### Shared rules

| Key | Default | Range | Meaning |
|---|---|---|---|
| `TripsPerWindow` | 10 | 1..100 | paid trips a character may make within `WindowHours`, all jobs together |
| `WindowHours` | 12 | up to 168 | length of the rolling window |
| `Pay` | 10 | 1..1000 | gold per delivery for a job without its own `Pay` |
| `MaxTripMinutes` | 15 | 1..120 | a trip still running after this is dropped |
| `MinDistance` | 1000 | | pickup and dropoff in one cell or worldspace must be at least this far apart |
| `MaxSpeed` | 150 | | units per second a delivery may average at most (see Anti-abuse) |

A value out of range is logged and the default is used.

### Job fields

| Field | Required | Default | Meaning |
|---|---|---|---|
| `Name` | yes | | unique (case-insensitive), at most 64 characters; the admin panel and the logs use it |
| `Enabled` | no | true | `false` keeps the job listed and visitable from the panel but never offered |
| `Item` | no | `load` | the noun in every message ("You pick up a hay bale.") |
| `Prompt` | no | `Carry <Item>` | the offer's wording before the pay, `Carry hay` in `[E] Carry hay (10 gold)` |
| `Pay` | no | the shared `Pay` | whole gold, 1..1000 |
| `CarryAnim` | no | `OffsetCarryBasketStart` | an `Offset...` behaviour event; observers only see it when it is in the client's `forcedSyncAnims` (`skymp5-client/src/sync/animation.ts`), which holds `OffsetCarryBasketStart` and `OffsetCarryLogStart` |
| `Requires` | no | none | editor ids, load-order ids (`0x0010ACCC`) or descs (`10accc:Skyrim.esm`); the player must hold any one of them. An entry may be an item, a form list (every item in it counts) or a keyword (any held item carrying it counts) |
| `RequiresText` | no | `the right tool` | "You need `<RequiresText>` for this work." |
| `Rewards` | no | none | items added with the gold at every paid delivery and named in the payment notice. Each entry is `"id count"`, `{ "ID": id, "Count": n }` or `{ "OneOf": [ids], "Count": n }`, where one of the `OneOf` ids is picked at random per delivery; ids are editor ids, load-order ids or descs of item records. `Count` 1..100, at most 8 entries and 64 ids per entry |
| `Pickup`, `Dropoff` | yes | | `ID`: the cell indoors or the worldspace outdoors, as an editor id (`Tamriel`, `WhiterunWorld`), a desc (`3c:Skyrim.esm`) or a load-order id; `POS`: `{x,y,z}`, `[x,y,z]` or `"x, y, z"`; `Radius`: default 200, clamped to 50..2000; `Label`: how messages name the spot ("the stable") |

`ID` resolves exactly like an NPC zone's (see `docs_roleplay_npc_spawns.md`,
ID resolution), `Requires` editor ids are looked up among the `FLST`,
`KYWD`, `WEAP`, `ARMO` and `MISC` records of the load order, and `Rewards`
editor ids among the item records (`WEAP`, `ARMO`, `AMMO`, `ALCH`, `INGR`,
`BOOK`, `MISC`, `KEYM`, `SCRL`, `SLGM`, `LIGH`).

The template pays Haybales 1 Straw (`BYOHMaterialStraw`, HearthFires.esm) and
Fishing one raw fish at random: the 23 raw fish the cooking recipes of
`ccBGSSSE001-Fish.esm` take, 15 food fish (`ccBGSSSE001_Food<Fish>`) and 8
ingredient fish (`ccBGSSSE001_<Fish>Ing`); the juvenile mudcrab and crab meat
are left out. Woodblocks pays gold only. The Rare Curios ingredients and the
Amber and Madness ores have no job or other source: staff hand them out with
the admin item spawn.

A job fails closed. An enabled entry is skipped, with one log line naming the
reason, when a location does not resolve, a `POS` is unusable, the two ends
share a cell and lie closer than `MinDistance`, `Pay` or `CarryAnim` is
invalid, a `Requires` entry is not in the load order or is not an item,
form list or keyword, or a `Rewards` entry is malformed or names anything but
an item of the load order. The fishing rod keyword and the raw fish come from
`ccBGSSSE001-Fish.esm`, which is not in `loadOrder` until the Creation Club
content is added, so an enabled Fishing job logs
`[jobs] 'Fishing' skipped, Requires 'ccBGSSSE001_FishingPoleKW' is not in the load order`
and stays off until then. Disabled entries log no reasons; the panel shows them.
Two entries sharing a `Name` load once, the first wins.

The template's placeholder coordinates put both ends on `0, 0, 0`, so the panel
lists them as `Disabled, pickup and dropoff are 0 units apart` until real spots
are set.

## Taking the work

1. Every second the server checks who stands within `Radius` of an enabled
   pickup and sends that player the offer; it is withdrawn once they are
   beyond 1.25 x `Radius`, so standing at the edge does not flicker it.
2. The client shows the offer in the activate prompt's place whenever nothing
   under the crosshair has a prompt of its own, as one line in sentence case:
   `[E] Carry hay (10 gold)`, the job's `Prompt` and its pay. The key is read
   from the Activate binding (a letter key; any other binding shows the line
   without it), since with no target the vanilla key glyph is not on screen.
   While riding no offer shows. With `customPrompts: false` in the client
   settings no offer shows at all, but Activate on nothing still takes the work.
3. Activate with nothing under the crosshair sends `jobStart`. The server
   checks, in this order, and answers with a notice (repeats within a second
   are not repeated):
   - still within 1.25 x `Radius` of the pickup, else "Stand at the hay pile to take this work."
   - the limit: "You have made 10 trips. There is more work in 3 h 12 min."
   - `Requires`: "You need a woodcutter's axe for this work."
   - not bound or carried, and not carrying a body or a pet: "Your hands are full."
   - not mounted: "Dismount to pick up the block of wood."
   - weapon sheathed: "Put your weapon away to pick up the block of wood."
4. On success the offer is withdrawn, the client gets `carryState` (carrying,
   the job's `CarryAnim`, target 0) and `jobState` (the title "Block of wood for
   the mill"), and the player reads "You pick up a block of wood. Carry it to the mill."

Several players may work one pickup at once; there is no queue.

### The walk

`RestraintService` applies the same carrier state as carrying a person: the
pose, `CarryWeight -10000` (forced walk, no sprint or jump), no fighting and a
forced sheathe, and emotes are refused with "Put down what you carry to use
emotes." (the same text a player carrying a person or a pet reads; bound or
carried players still read "You cannot use emotes while restrained."). The
carry weight change is local to the game session: it is undone when the trip
ends, on a disconnect, and a crashed game simply starts without it.

Whether a basket or log appears in the hands is not verified; the offset poses
may show arms loaded and nothing else. Test `player.sae OffsetCarryBasketStart`
and `player.sae OffsetCarryLogStart` in single player first.

### Delivery

Walking within `Radius` of the dropoff ends the trip:

- A trip faster than allowed is not paid: "That was too quick; nobody pays for that."
  The minimum is 10 seconds, or the straight distance from the edge of the
  pickup offer (1.25 x its `Radius`) to the edge of the dropoff divided by
  `MaxSpeed`, whichever is longer. Ends in different cells use the 10 seconds.
- Otherwise the gold and each `Rewards` entry are added silently (`AddItem`),
  the delivery time is stored and the player reads
  "You deliver the block of wood and earn 10 gold. 7 of 10 trips left.", with
  rewards "You deliver the hay bale and earn 10 gold and 1 Straw. 9 of 10 trips
  left.", or on the last one "You deliver the block of wood and earn 10 gold.
  That was your last trip; there is more work in 11 h 40 min."
- Reward names are the items' in-game names, read once from the plugins
  (localized strings included); an item without a name shows its id from the
  file. A reward the server cannot add is logged and left out of the notice;
  the gold and the trip still count.

Jobs are pure income: a delivery never adds mastery hours.

## The limit

`private.jobs.trips` on the character holds the time of each paid delivery. A
trip is allowed while fewer than `TripsPerWindow` of them fall within the last
`WindowHours`, so each trip becomes available again `WindowHours` after it was
made. The server clock is used, so time offline counts. The limit is checked
when a trip starts and again at delivery; cancelled and unpaid trips never
count. It is per character (`characterSelectMaxCharacters` is 1 today, so per
account in practice).

To test many trips, lower `WindowHours` in the file for a moment; the reload
applies it to every character at once.

## What ends a trip

Every ending for a player still connected sends `carryState` false and clears
`jobState`, and none of them costs a trip.

| Cause | When it is seen | Message |
|---|---|---|
| Put down in the player action menu | at once | "You put the block of wood down." |
| A hit landed on the carrier (after every other hit handler allowed it) | next poll | "You dropped the block of wood in the fight." |
| Weapon drawn, more than 3 s into the trip | poll | "You dropped the block of wood to draw your weapon." |
| Mounted (`ff_mount`) | poll | "You dropped the block of wood to mount." |
| Dead, bleeding out, bound or carried | poll | "You dropped the block of wood." |
| A cell or worldspace change, except one move into the dropoff's own cell when the ends differ | poll | "You dropped the block of wood." |
| More than 600 units per second between two polls (teleport, admin TP or summon) | poll | "You dropped the block of wood." |
| `MaxTripMinutes` passed | poll | "You took too long and dropped the block of wood." |
| The job was removed or edited in `Jobs.json` | reload | "The work here has changed." |
| Character select | at once | none; the connection stays, so the client is told to drop the pose |
| Another character assigned to the connection | at once | none |
| Disconnect | at once | none, the client clears the pose itself |

A trip may therefore cross one load door, into the dropoff's cell or worldspace;
place both ends at most one door apart.

### Put down

While a load is carried, the player action menu gains **Put down**: the
interact key (X) on nothing opens a small menu titled with the load ("Block of
wood for the mill") holding **Put down** and **Personal Menu**, and the menu
on another player lists Put down too. The title is the reminder of where the
load goes.

### Interplay with other systems

- **Fighting**: the carrier's own attacks and spells are refused server-side
  (`onHitAttempt`, `onHitDamageAttempt`, `onSpellCastAttempt`). The job hooks
  are the outermost wrappers (JobSystem is pushed last in `index.ts`) and call
  the previous handler first, so god mode, the capture block and the
  companion checks still decide first, and a hit they refuse never drops a load.
- **Carrying people and pets**: a job carrier cannot carry a player or a pet
  ("Put the block of wood down first.") and cannot be carried ("A stranger has
  their hands full."), through `CaptureSystem.jobLoadOf`. Being restrained is
  allowed and drops the load; the client keeps the bound pose when the carry
  ends after it.
- **Furniture**: activating furniture (chairs, benches, crafting stations,
  chopping blocks, mining markers) is refused with "Put the block of wood down first.",
  before any other activation handler, so no gathering session starts.
- **Grain mills** (the vanilla `GrainMill`, `0009C6DF`): the wheel is driven by
  the mill's own behaviour graph, which the engine feeds from its user's
  animation; a remote player's copy only replays the player's events, so
  observers saw a still wheel. `furnitureAnimationsService.ts` (client) keeps
  a table of such furniture: when a copy plays `IdleGrainMillEnter`, the
  nearest mill within 160 units gets `SlavePush` (through `playAnimation` and
  `Debug.sendAnimationEvent`, retried until its 3D is in); any later event of
  that copy, or the copy moving 96 units off or unloading, sends `SlaveIdle`.
  The platform log traces each send. The local user's own mill is the engine's
  business; if it turns out not to turn either, `furnitureSeatService` can send
  the same pair on `seatClaim` and `seatRelease`. A mill the plugin lists under
  `craftingStations` (spec, `docs_roleplay_mastery.md`) opens the crafting menu
  instead, so none of this runs there.
- Doors, containers, NPCs and trade work as usual.

## Anti-abuse

- Payment happens only in the server poll. The client sends just `jobStart`
  and `jobPutDown`; the server checks the location, the limit, the tool and the
  carrier state itself.
- Position, cell and the weapon state (`_skymp_isWeapDrawn`, read through
  Papyrus `IsWeaponDrawn`) are reported by the client, as for every other
  system. The per-poll jump check catches teleports and noclip, and the minimum
  trip time bounds a client that runs while forced to walk: an encumbered walk
  is roughly 80 to 110 units per second, so `MaxSpeed` 150 still pays a
  runner in about two thirds of the honest time. The hard cap is what bounds
  income: `TripsPerWindow` x `Pay` per character per window, 100 gold per 12 h
  with the defaults, whatever a bot does. Tune `MaxSpeed` down in testing if
  honest walkers never come near it.
- One trip per character; trips live in server memory, so a relog or a restart
  cancels them and nothing carries over.
- Refusal notices are throttled to one per second per player.

## Admin panel

Personal Menu > Admin > NPCs > **Jobs** (every tier with the `npcs` cap):

- The list shows every named entry of `Jobs.json`: a green dot and
  `Active · block of wood · 10 gold · 2 carrying` for a running job, a grey dot
  and the reason (`Disabled`, or why it was skipped) otherwise.
  - **TP pickup** / **TP dropoff** put the admin on that end's `POS` (a disabled
    job too, once its `ID` resolves); a carrier who is teleported drops the load.
  - **Edit** copies the entry into the form.
  - **Delete** removes the entry from the file (single click) and ends its trips.
- The form holds every field. **Set pickup here** and **Set dropoff here** fill
  that end's `ID` and `POS` with where the server has the admin right now (the
  desc of the worldspace outdoors or the cell indoors, the position to two
  decimals). The form survives closing the menu, so set the pickup, close the
  menu, walk to the dropoff, open the menu and set that too. **Save** is enabled
  once Name, both IDs and both positions are filled and the number fields hold
  numbers; the server validates like a file load (the `Requires` entries only
  with Enabled on, so Fishing can be placed and saved disabled before the CC
  plugin is in `loadOrder`, and still fails closed once enabled) and answers
  with a toast naming the first problem. A valid entry replaces the entry of
  the same name in place or is appended. **Clear** empties the form.
- The form has no `Rewards` field: a save keeps the `Rewards` of the entry it
  replaces (validated like `Requires`, only with Enabled on). Rewards are
  edited in the file by hand.

Save and Delete rewrite the whole file through a temp file and a rename,
keeping the wrapper's other keys; hand formatting is normalised. A file that is
not valid JSON blocks both until it is fixed by hand. Every change is written
to the admin log with the admin's profile.

## Hot reload

The file is watched with chokidar (`awaitWriteFinish`) and reloaded half a
second after the last write. Invalid JSON, or a top level that is neither an
array nor `{ "Jobs": [...] }`, keeps the previous jobs. A trip whose job is
unchanged keeps going; one whose job was removed or changed in any field ends
with "The work here has changed." Every offer is withdrawn on a reload and
made again at the next poll. Deleting the file at runtime removes every job.

## Logs

Prefixed `[jobs]` in the server log and the manager console:

- `N/M job(s) active from ./Jobs.json (boot | file changed | admin save | admin delete), disabled: ...; 10 trips per 12 h`
- `'<Name>' skipped, <reason>` for each enabled entry that does not load
- `<character> (<actor id>) picked up <Name>, 3/10 trips made`
- `<character> (<actor id>) delivered <Name>, +10 gold, +1 Straw, 4/10`
- `reward <item> for <character> (<actor id>) (<Name>) failed: <error>`
- `reward item names unreadable, the file's ids stand in: <error>`
- `<character> (<actor id>) delivered <Name> in 12 s, under the 17 s minimum, not paid`
- `<actor id> disconnected carrying <Name>`
- `refused onHitDamageAttempt by job carrier <actor id>` (at most every 5 s per carrier)
- `'<Name>' replaced in` / `appended to` / `removed from ./Jobs.json by admin`

## Deployment

- Server: manager **Build server**, restart the game service.
- Client and front (offer prompt, Put down, the `OffsetCarryLogStart` sync
  and the Jobs sub-tab): manager **Build Client**; players re-download through
  the launcher. An old client against the new server never sees an offer.
- Server manager: restart the manager app, so a **Build server** keeps
  `Jobs.json` (added to the deploy prune's keep list).
- `Jobs.json` lives in `build/dist/server/`, is gitignored and is not carried by
  a commit: create it on the box from the template above.
- No gamemode build, native build or plugin change.
