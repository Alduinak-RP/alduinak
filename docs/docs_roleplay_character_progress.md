# Character progress — map markers and ingredient effects that survive a relog

SkyMP starts every session from a fresh engine state, so the world map forgets
every location the character found and the alchemy menu forgets every
ingredient effect it tasted. The client now keeps both in a small local file
per character and replays them a couple of seconds after the character spawns.
Nothing is sent to the server; the server neither knows nor cares.

- Client piece: `skymp5-client/src/services/services/characterProgressService.ts`
- Marker table: `skymp5-client/src/data/mapMarkerRefs.ts` (generated, see below)
- Generator: `skymp5-client/scripts/gen-map-markers.js`
- Save file on each player's PC: `Data/Platform/PluginsNoLoad/character-progress-no-load.js`

---

## What is saved

| Kind | Read with | Restored with |
|---|---|---|
| Discovered map markers | `ObjectReference.isMapMarkerVisible()` on every REFR of the marker table | `addToMap(true)` when the marker is not visible yet |
| Learned ingredient effects | `Ingredient.getIsNthEffectKnown(i)` for the first four effects of every carried ingredient plus every ingredient already in the save | `learnEffect(i)` for every saved `true` bit that the engine does not know yet |

A bit that was once saved as `true` is never cleared, so a marker or effect
that vanished from the engine (respawn, relog, hot reload) comes back.

Timing:

- Markers are scanned in chunks of 60 per frame, one full pass every 10 s and
  an extra pass right after a `locationDiscovery` or `cellFullyLoaded` event.
- Ingredients are polled every 5 s, 0.7 s after the player eats an ingredient
  and as soon as the Crafting menu closes. A poll collects the carried and
  saved ingredients in one frame (`Ingredient.from` casts, no Papyrus call)
  and then reads their known effects at 5 ingredients per frame.
- The file is written 2 s after the first change (debounced) and flushed when
  the Main Menu opens, when the own actor is destroyed (character switch,
  park) and on disconnect. Every write re-reads the file and replaces only the
  current character's entry; a failed write keeps the entry dirty and retries
  2 s later.
- Restore starts 2.5 s after the first in-game frame following the own
  `createActor` message and drains at 25 native calls per frame. Nothing is
  recorded until the restore queue for the current character has drained, so
  the replay never writes itself back as new progress.
- Single player mode skips the whole service.

## The file

Written as `//` followed by JSON, read back with `data.slice(2)`, the same
mechanism as `chat-settings-no-load`.

```json
{
  "version": 1,
  "characters": {
    "1.2.3.4:7777/ff000abc": {
      "name": "Lydia",
      "updatedAt": 1756900000000,
      "markers": ["162f0:Skyrim.esm", "d0e:Warbirds Whiterun Metropolis.esp"],
      "ingredients": { "34d22:Skyrim.esm": [true, false, false, true] }
    }
  }
}
```

- The character key is `<server-ip>:<server-port>/<remote actor id hex>` from
  the client settings and `RemoteServer.getMyRemoteRefrId()`, so the same
  actor id on two different servers never collides.
- Forms are stored as `<local id hex>:<Plugin file>` and resolved at runtime
  with `Game.getFormFromFile`, so a load order change cannot point a saved id
  at the wrong form. Runtime ids are turned back into that form with the
  client's own load order (`Game.getModName`, `Game.getLightModName` for
  ESL-flagged plugins in the `0xFE` space).
- Caps: 30 characters per file (the oldest `updatedAt` is dropped first),
  3000 markers and 1500 ingredients per character.
- The in-memory sets live in `sp.storage`, so a client hot reload keeps
  unwritten progress, and a reload inside the restore delay resumes the
  restore on its first update.

## The marker table

Skyrim Platform has no way to enumerate map markers at runtime, so the client
ships a constant list of every REFR whose base object is the `MapMarker` STAT
(`Skyrim.esm` `0x10`) in the server load order. The generator walks every
plugin with the same TES5 GRUP/record walker as
`skymp5-server/ts/systems/espmEditorIds.ts`, follows the CELL and WRLD trees,
resolves the REFR's `NAME` through the plugin's master list, skips deleted
records and lets a later override drop a marker that stopped being one.
Overrides of a vanilla marker keep the vanilla `hex:Skyrim.esm` id.

```
cd skymp5-client
node scripts/gen-map-markers.js
node scripts/gen-map-markers.js --data "X:/Skyrim/Data" --load-order "Skyrim.esm,Update.esm,Dawnguard.esm"
```

Without arguments it reads `loadOrder` and `dataDir` from
`build/dist/server/server-settings.json`. `--load-order` accepts a JSON file
(an array, or an object with `loadOrder` and optionally `dataDir` keys, a
relative `dataDir` being resolved against that file) or a comma list; relative
entries are looked up under `--data`, else the settings `dataDir`, else the
current directory. Master names in a plugin header are matched to the load
order spelling case-insensitively. The script prints the marker count per
plugin and rewrites `src/data/mapMarkerRefs.ts`, then the client needs a
"Build Client" so players pick it up. It exits 1 without touching the table
when `Skyrim.esm` (or the first plugin) is unreadable or no marker was found.

## Limitations

- The save is per PC, not per account. Another machine or a reinstall starts
  with an empty map and no known effects; a server-side mirror would be the
  durable fix.
- `addToMap(true)` also sets the per-marker fast travel flag, like natural
  discovery. Fast travel stays blocked by the global
  `Game.enableFastTravel(false)` in `disableFastTravelService.ts`. Whether the
  replay shows the vanilla "location discovered" toast per marker is
  unverified; if it does, lower `RESTORE_BATCH` in the service.
- Learned effects and marker visibility are global engine state, so after a
  character switch inside one session the second character inherits whatever
  the first one learned until the game is relaunched; the poller records that
  as the second character's progress.
- Regenerate the table after adding or removing a plugin that places map
  markers, otherwise those markers are never recorded. A saved marker whose
  plugin is gone simply resolves to nothing and is skipped.
- Two game instances on one PC share the file. Each write merges only its own
  character into a fresh read, so they do not erase each other's entries; two
  writes in the same instant can still race, and the loser's entry comes back
  on its next write.
