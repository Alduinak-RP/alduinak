# Durability: the condition of weapons and armor

Every copy of a weapon, bow, crossbow, armor piece or shield has a condition. The native server wears it
down on hits, the client shows it in the item's name ("Steel Sword (97%)", "(Broken)" at 0) and a workbench
or grindstone repairs it. The whole feature is behind `alduinakDamageFormulaSettings.durability.enabled` in
`server-settings.json`; without the block, or with that key not `true`, nothing below runs and every
inventory, trade and craft behaves as before.

This document covers how the condition travels through the server TypeScript. The damage formula and the
`/armor` readout are in `docs_onhit_and_damage.md`.

## The value

- `condition` is a field of an inventory entry (`Inventory::ExtraData` in the native, `Extras.condition` in
  `skymp5-server/ts/systems/inventoryExtras.ts`). It is a share from 0 to 1. A pristine copy has no field, a
  broken copy has `condition: 0`.
- The percent in the name is `conditionPercent`: rounded down, never 0 above broken, 100 without a value.
  The client (`sync/durabilityNames.ts`) and the native use the same rule.
- Only the server sets it. A condition a client sends (a trade offer line, a craft report) only says which
  copy the player means.

## Identity and stacking

| Function (`inventoryExtras.ts`) | Condition |
|---|---|
| `sameItem`, `lineKey`, `hasIdentityExtras` | Ignored. A worn copy is the same item to a client, as with the charge of a weapon |
| `sameExtras`, `addEntries` | Compared. A worn copy never stacks onto a pristine one, and two worn copies stack only at the same stored value |
| `withCount`, `{ ...entry }` copies | Kept, so a moved copy carries its condition |
| `copyValidExtras` | Accepts 0 up to but not 1 from a client, as a hint |
| `describeExtras` | Logs `condition=0.43`, and `condition=0` for a broken copy |
| `byNearestCondition` | Orders entries for a draw: the same percent first, then the nearest |
| `withoutCondition` | The copy as it is when pristine |

Code that moves entries must copy them whole (`withCount`, a spread, `addEntries`) and never rebuild them from
a list of keys. Papyrus `AddItem` (`addItemTo`) always gives a pristine copy, so it is right for new items and
wrong for moving an existing one.

## Settling wear before items move

The native keeps the wear of a running fight in memory and writes it into the copies every few seconds.
`settleWear(actorId)` writes it at once. Server TS calls it through `systems/durabilityNative.ts`
(`wearSettler`), the one file that names the native function and the settings keys:

| Where | When |
|---|---|
| `tradeSystem.ts` | When the trade window opens (both sides), on every offer change and lock (that side), and before the swap (both sides) |
| `bodySystem.ts` | Before a PK body takes the victim's pack |
| `searchSystem.ts` | When a search or loot window opens, for the actor being searched |
| `afterlifeSystem.ts` | Before the realm outfit is taken back |

With durability off the native is never called. With durability on and a `scam_native.node` that has no
`settleWear` the server logs once at boot

    [durability] wear is not settled before items change hands: this scam_native.node has no settleWear, an item traded or taken right after a fight keeps the condition it last showed

and everything else works. A call that throws is logged once (`[durability] settleWear failed for <actor>`).

## Trade

- An offer line may carry `condition`. The server first draws, for every line, the copies that show exactly
  that percent, then the nearest ones. A line without a condition means a pristine copy and falls back to the
  best copies the player holds.
- One offer keeps one line per item and shown percent, the same split as the client's rows.
- `theirOffer` in `tradeState` lists the server's own copies with their condition, so the buyer sees the true
  value. `myOffer` echoes the lines as offered.
- The copy that changes hands keeps the server's condition, never the offered one, and lands in the buyer's
  pack as an entry of its own.
- When both have locked and the offer would now move another worn copy, or the same copy after more wear,
  than the one shown at the lock, the swap does not happen. Both locks are released, both players read
  "An offered item is no longer in the condition shown. Check the offer and lock again." and the window shows
  the copy that would move. Offers of pristine items never take this path.
- `[trade]` lines and `trading.log` list the condition of each moved copy (`{condition=0.42}`).

## Crafted extras (enchanting, tempering and poison done in the vanilla menus)

- The result of a reported craft keeps the condition of the server copy it was made from. A craft never
  repairs, whatever the report says.
- A lost line with a condition claims the server copy nearest to it, so tempering the 40% sword changes the
  40% sword.
- A poison applied to the worn weapon goes onto the copy at the condition of the equipment entry.
- The name a player gives an enchanted item loses a trailing condition tag, also when the engine put the
  quality after it ("Steel Sword (97%) (Fine)" is stored as "Steel Sword"). The broken word is
  `durability.nameTag.brokenLabel` (default `Broken`). With durability off names are cleaned as before.

## Other systems

| System | What happens to the condition |
|---|---|
| PK body (`bodySystem.ts`) | The pack moves entry by entry; worn and pristine copies stay apart on the body and in the looter's pack |
| Search and loot windows (`searchSystem.ts`) | The native moves the server's copies; the window itself lists plain stacks without a tag |
| Skinning (`huntingSystem.ts`) | A stack of the body that carries a condition moves as its entry; plain stacks go through `AddItem` as before |
| Afterlife outfit (`afterlifeSystem.ts`) | A granted piece is taken back however worn it is; the player's tempered or enchanted pieces stay |
| Pets (`petSystem.ts`) | A stored pet keeps its whole inventory record, conditions included |
| Housing storage, containers | Native put and take, which move the server's copies |
| Admin item spawner, kits, starting items | New pristine copies; they never join a worn stack |
| `deploy/mongodb/restore-stripped-items.js` | A copy is matched by all its extras, so a worn copy from the backup comes back worn and beside the pristine ones |

## Client: the tag in the name

The client shows a condition only after the server sent the custom packet `durabilityConfig`
(`showAtFull`, `brokenLabel`, optional `enabled`). `RepairService` stores it through
`sync/durabilityNames.ts` and forgets it at every new connection, so on a server that never sends the
packet no name is tagged, cut or renamed and every message is as before.

| Part (`skymp5-client/src`) | What it does |
|---|---|
| `sync/inventory.ts` | `Extra.condition`. `extrasEqual` does not compare it, so a condition change is no inventory difference and never removes and re-adds a copy. A server copy is added through `addItemEx` under `durabilityName` ("Steel Sword (97%)"); a local copy is removed under the name it carries, the copies whose tag the server no longer holds first |
| `sync/durabilityNames.ts` | `isDurable` (weapons except staffs and bound ones, light and heavy armor, shields), `tagFor`, `stripTag`, `conditionPercent`, and `applyDurabilityNames`, the rename pass |
| `services/services/remoteServer.ts` | Runs the rename pass right after the player's `applyInventory`, so never with an inventory, container, favourites, magic or crafting menu open. A base the same apply still adds to or removes from waits for the next one |
| `services/services/containersService.ts`, `dropItemService.ts` | A put, take or drop of a durable item sends the tagged name of each moved copy, one message per tag, and no `condition`; the native picks the copy by that tag. A dropped or put copy without a tag takes the tag the pack lost: the server's tags of that base minus the tags still in the pack, when exactly the moved count is left and they agree |
| `services/services/tradeService.ts` | One row per item and shown percent, the percent as a tag beside the temper tag, `condition` in the offer lines as the hint |
| `services/services/craftedExtrasService.ts` | A reported name has no tag, and the lost line names the copy at the changed copy's tag |
| `services/services/repairService.ts` | Stores `durabilityConfig`, mirrors `repairMenu` into the `repairMenu` widget and sends `durabilityRepair`, `durabilityImprove` and `durabilityClose` |

The rename pass compares, per durable base and per group of copies with the same extras, the tags the server's
entries ask for with the raw local copies (`getRawEntries`, one per extra list, since `getInventory` merges
copies that differ only by name). A tag the server still holds stays where it is, on unworn copies first, so a
changed one lands on the worn copy; the others take the nearest percent.

- With `setInventoryItemName` in SkyrimPlatform (looked up on every pass, so a dll without the export only
  loses this path) a copy is renamed in place, worn or not: no unequip, no flicker. Two extra lists of the
  same name and worn state are renamed only when nothing else tells them apart (same extras, same count), and
  a stack of which only some copies changed stays whole and keeps its tag.
- A copy in an extra list is never removed and added again for its tag: the favorite mark and the 1 to 8
  hotkey live in that list, the client cannot read them, and a copy put in again would lose both. So without
  the export such a copy keeps the tag it was added under, worn or not (a piece worn at login has none), until
  the next login; `/armor` and the repair menu show the true condition.
- A copy without an extra list (picked up, crafted) holds no favorite mark, so it is removed and added again
  under its tag, with or without the export. While a spawn's outfit settles nothing is re-added either. The
  pass never takes a worn item off.
- `skyrim-platform.log` gets one line when the server switches the tags on ("condition tags on: ..." with
  whether the in-place rename is there), and at most one a minute while copies keep an old tag.
- After durability went off in a session that wrote tags, the pass takes them out again, by the same rules.

The quality the engine appends ("(Fine)") comes after the tag and is never part of a name the client writes.
In the trade window a name on something that never wears is left alone, percent sign or not.

## Front: the repair menu

`skymp5-front/src/features/repairMenu` draws the `repairMenu` widget (id 42) in the red panel look of the
housing and trade menus; `constructor.js` maps the type and `App.js` keys it by id, so a refresh keeps the
open menu and its scroll position.

- The title is the server's (`Workbench: repair armor`, `Grindstone: repair weapons`), with the number of
  damaged items under it.
- One row per damaged copy in the server's order: the name with an `equipped` mark on a worn copy, a condition
  bar (bright under 25%), `43% (150/350)` (the percent alone when the row has no hit points, `Broken` at 0),
  and the cost as `2 Steel Ingot (have 5)`, red for a material the player is short of, `No materials needed`
  for a free repair.
- Repair sends `repairMenu:repair` with the row's key as it came and is off while any material is short.
- The footer: Repair all (`repairMenu:repairAll`, off when no row can be paid), Improve items
  (`repairMenu:improve`) and Close (`repairMenu:close`). With no rows left it reads "Nothing left to repair"
  and keeps the footer.
- After a Repair or Repair all the repair buttons stay off until the server's refresh arrives, at most 1.5 s
  (a refusal for distance sends no refresh), so a double click never asks for the same copy twice.
- Escape and losing the browser focus close the menu, as in the other menus.
